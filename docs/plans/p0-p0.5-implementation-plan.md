# P0 — Security, governance, consent, evidence-integrity regression protection

## P0-1 · Analytics view exposure (SECURITY — first post-merge remediation)

**Defect.** The four `0008_analytics_views.sql` views (`analytics_people_served`,
`analytics_participation_classification`, `analytics_service_events`, `analytics_residence_occupancy`)
are plain (owner-privileged) views swept into `0110_table_grants.sql`'s blanket
`grant select … to authenticated` + default-privilege rule. Any authenticated user can read all-person
service events and residency classification through PostgREST. No app/package consumer exists (verified).

**Change.**
- New migration `supabase/launch/migrations/0125_analytics_view_security.sql`:
  - `alter view … set (security_invoker = true)` on all four views (defense in depth), and
  - `revoke select on <each view> from anon, authenticated` (primary fix; service_role retains access
    for internal analytics).
  - Header documents the standing rule: every future `recoveryos` view must either set
    `security_invoker = true` or explicitly revoke client-role privileges (the 0122 pattern), because
    0110's default privileges also capture views.
- `supabase/launch/preflight/launch_contract_check.sql`: new step 9 — iterate
  `pg_views where schemaname='recoveryos'`; FAIL if `has_table_privilege('authenticated', view, 'select')`
  is true and the view's `reloptions` lack `security_invoker=true`. Allowlist:
  `residence_directory_public` (deliberately owner-privileged curated anon surface, documented in 0122)
  and `check_ins_staff_view` (already `security_invoker`).
- New static guard `scripts/verify-view-privileges.mjs`: scans `supabase/launch/migrations/**` for
  `create view`/`create or replace view` statements and fails unless the same file (or an allowlisted
  later migration) sets `security_invoker` or revokes client privileges. Wired into
  `.github/workflows/ci.yml`.

**Tests.** Preflight step against staging; launch-tests matrix row: unknown-JWT and fixture-participant
reads of `analytics_people_served` must be denied.

**Live implications.** Revokes privileges on four unused views. Gate R-1 precheck: scan Supabase API/query
logs for any access to the four view names in the trailing 30 days before applying; an unknown external
consumer converts this into a coordinated change.

**Rollback.** `grant select … to authenticated` per view + `alter view … reset (security_invoker)` —
exact statements staged in the migration header.
